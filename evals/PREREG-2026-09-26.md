# Pre-registered test: does a spreadsheet brain make an AI better at a workbook?

Written 2026-09-26, before any data for this test exists. The analysis below is fixed now and is followed as written. Anything done differently is reported as a deviation.

## Question

When an AI with no skill and no hint is handed a workbook, does a brain built by this skill (the `_brain` tab, made by the owner answering the skill's questions) make its answers better than the same workbook without a brain?

## Design

- **Trial:** one business b, one model m, one repetition r, one condition c (no brain, brain). Paired unit: (b, m, r).
- **Businesses:**
  - Held-out set H (primary): 4 new synthetic businesses built after this plan by agents that never read this repo, each with a workbook, an owner brief and an answer key computed by code. Planned: restaurant inventory counts, payroll, online store order lines, property rent roll (the last one has no playbook in the tool, so it tests the generic path).
  - Development set D (secondary, reported separately): the hotel purchasing (with two added months), SaaS finance model and bakery books used while tuning the tool. Results on D are expected to flatter the tool and never count toward the primary result.
- **Brains:** built by an agent playing the owner from the brief, running the full skill (questions, save). A gate before any answer run: every brain must hold at least one owner note, and a checker compares each owner note with the brief. A brain that fails the gate is rebuilt, never hand-edited.
- **Models (no skill, cold):** Claude Haiku 4.5, Claude Sonnet 5, Claude Opus 5.5, OpenAI GPT-5.6-Luna (Codex CLI). Each gets only its folder and Python with openpyxl.
- **Repetitions:** 2 per (business, model, condition).
- **Prompts:** per business, one message holding one open request (what should I pay attention to, or the like, written by the business builder) and three plain questions with exact answers.
- **Test files:** the fixture description property is stripped; file names and data are identical between conditions except for the `_brain` tab.

## Measures

- **Primary:** the open-request score, 0 to 15 (on target 0 to 5, right 0 to 5, useful 0 to 5), given by two independent blind judges who see the brief and the key, and see the two answers of a pair in random order without knowing which had the brain. The pair's score per condition is the mean of the two judges.
- **Secondary:**
  1. Plain-question accuracy: each of the 3 answers graded correct or not against the key (within 1% or the key's rounding) by a blind grader.
  2. Mistakes the owner would catch, counted by the judges (mean of two).
  3. Judge preference: which answer of the pair is better (the mean of the two judges' picks, ties allowed).

## Analysis (fixed now)

- **Primary test:** Wilcoxon signed-rank test, two-sided, alpha 0.05, on the paired differences (brain minus no brain) of the primary score across all held-out pairs (4 businesses x 4 models x 2 repetitions = 32 pairs). Reported with the mean and median difference and a 95% confidence interval from a bootstrap that resamples businesses (10,000 resamples), because pairs within a business are not independent.
- **Secondary tests:** McNemar's exact test on plain-question outcomes (brain vs no brain, per question and pair); Wilcoxon signed-rank on mistake counts; exact sign test on preferences (ties dropped).
- **Breakdowns (described, not tested):** per model, per business, and the development set.
- **Judge agreement:** Spearman correlation between the two judges' scores, reported.
- **Missing answers:** a run with no answer is re-run once; if it fails again its pair is dropped and reported.

## Integrity

- The tool is frozen for this test: the repo snapshot and its sha256 are recorded below before any held-out business exists. No change to the tool between this plan and the analysis.
- Answer agents never see the brief or the key. Judges never see which answer had the brain. Business builders never read this repo.
- Every trial, judge score and exclusion is kept in the results file and reported.

### Deviations from the plan above, fixed before any data

1. **Held-out businesses were built before the freeze, not after.** They were built by agents that never read this repo, and the tool was never run on them before the freeze (no brain store on this machine holds any of their files). The only tool changes made after they existed came from a test on the development hotel file (a later AI picking up a brain): the reader now reads rows another AI added the same way every time, takes one row per id, leaves superseded counted notes out when answering, and the tab's note on how it grows names every column.
2. **Clean room for answer runs.** Claude models run through the Claude Code CLI with no user or project settings, no instruction files, no MCP servers and a sandboxed shell: `claude -p <message> --model <m> --setting-sources local --strict-mcp-config --no-session-persistence --settings '{"sandbox":{"enabled":true,"autoAllowBashIfSandboxed":true}}'`, started inside the trial's folder. GPT-5.6-Luna runs through `codex exec --skip-git-repo-check -s read-only -m gpt-5.6-luna -C <folder>`. (A pilot run through in-session subagents picked up this machine's own instructions, so subagents are not used for answers.) A run that has not finished in 20 minutes counts as no answer.
3. **Judges from two model families.** Judge 1 is Claude Opus 5.5 (same clean room, with `--json-schema`), judge 2 is OpenAI GPT-6-Astra (Codex CLI, `--output-schema`). Each sees the owner's brief, the key, the request and the two answers of a pair as A and B in an order set by a coin flip recorded in the results file. Answers are not edited, so an answer that mentions a notes tab can reveal its condition; how often answers do so is reported.
4. **Plain-question grading.** Both judges grade the plain questions of both answers. The primary grade is judge 1's; agreement with judge 2 is reported. Rules: a number is correct within 1% or the key's rounding; a named answer must match; an answer that computes a different thing than the key's question is wrong; a question with several parts (per hotel, branch and hours, tenant and amount) is correct only if every part is; a question asking for a list is correct if it names every item in the key (extra items do not make it wrong).
5. **Prompts.** Every trial gets one message: "I just got {this file / these files} from a colleague: {file names}. {open request} Also: (1) {q1} (2) {q2} (3) {q3} Python 3 with openpyxl is at /usr/bin/python3 if you want to open the files. Work numbers out from the files; don't guess. Answer in plain words, under 500 words total."
6. **Development set questions.** Hotel (the purchasing workbook with July and August 2026 added, and its contracts file): total store spend January 2025 through August 2026; each hotel's spend in July and August 2026; the rebate Coastline Provisions owes on 2025 purchases. Finance: which formulas look like mistakes; what the Growth input means; the lowest cash month. Bakery books: 2025 net income; how much Dana took out in 2025; the biggest item sitting in suspense and where it belongs. Held-out questions are the three in each business's key, as written by its builder.
7. **Run settings.** GPT-5.6-Luna runs at reasoning effort medium (set explicitly, so this machine's own Codex setting does not apply); judge 2 (GPT-6-Astra) at effort high; Claude models at the CLI's default effort. Each trial gets its own folder holding only its workbook copies. Trial order is fixed by a seeded shuffle of (business, model, repetition) units, with the unit's two conditions run back to back in a seeded random order; at most 5 Claude and 3 Codex trials run at once. A run stopped by a usage limit is not a failure: it is run again after the limit resets. The runner and judge scripts are kept with the results.
8. **Brains.** Each brain is built by one agent (Claude Opus 5.5) playing the owner, answering the tool's questions only from that business's brief ("Not sure" where the brief is silent), in its own brain store, on a copy of the workbook. The gate runs on each saved file before any answer run: the tab exists and holds at least one owner note, and two checkers (Claude Opus 5.5) read every owner note against the brief, one looking for contradictions and one for owner claims the brief never makes. A brain with any such note is rebuilt from scratch until one passes, never edited, and every attempt is reported. A code check confirms each brain copy holds exactly the source workbook's data plus the `_brain` tab.

### Changes after the freeze, before any answer run

9. **A writer fix, forced by the held-out set (2026-09-26 11:58).** The frozen tool could not write a brain into any of the four held-out workbooks: they were saved by openpyxl without lxml, which declares the relationships namespace on each sheet element instead of the workbook's root, and the writer required it on the root. It then fell back to keeping the brain on the machine while still reporting success. The fix is 7 lines in `sheetbrain/brainzip.py` (`_add_to_workbook_xml` declares the namespace on the brain's own sheet element when the root does not), plus one regression test; no change to questions, notes, reading or analysis. Only that one file differs from the frozen manifest; the new manifest is `evals/FREEZE-manifest-2.sha256` (sha256 `46b0aa7af61abd4f73109ac5336820ae6d473cb485fd6c119e28f24af873525d`); 218 tests pass. The four held-out brains were saved again from their first builds' stored answers with the fixed writer (no new questions asked). Writing a brain into each of the 8 test workbooks, reading it back and removing it restores every original byte for byte.
10. **Which build is used.** The first build that passes the gate is used. Finance: build 1. Hotel: build 1 failed the gate (a "per case" price basis the owner never gave, among others), build 2 passed. Bakery books: builds 1 and 2 failed (the tool's goal and leave-out options added "monthly P&L" and "owner contributions", which the owner never said, and the owner agent picked the closest option). From build 3 on, the owner agent is also told to type the brief's own words when no option says exactly what the brief says. Held-out: build 1 of each, gated after the re-save above. Stopping rule, set while build 4 of the bakery books was still running: a business gets at most 4 builds; if none passes, it is left out of the analysis and reported, because a brain that puts words in the owner's mouth tests the filler, not the tool. (Held-out gate result: all four passed on build 1.) Bakery books: builds 3 and 4 failed the same way (the tool files the owner's typed goal, a P&L by class to close 2025 for the CPA, under its 'monthly P&L' option), so by the stopping rule the bakery is left out, and the development set is the hotel and the finance model (16 pairs).
11. **Findings from the builds, not fixed (the tool stays frozen):** save reports success when the tab could not be written; answer options can put words in the owner's mouth; on the held-out workbooks the tool never asked about most of the owner's key rules (for example waste reason code 4, the paymaster branch, the discount unit change, the bounced-payment status), which the owner agents added only where a free-text question let them. These are reported with the results and left for the next version.
12. **Isolation, tightened after two smoke trials (both discarded, kept aside, never analyzed).** The smoke trials showed that trials inherited this session's environment (session variables, including an effort setting) and that GPT-5.6-Luna searched the folders above its own, listing other test workbooks there (it opened none). From here on: each trial runs in its own new root folder (`/private/tmp/sbt-<hash>/work`) holding only its workbook copies, with a scrubbed environment (home, user, path, shell, language, and a temp folder inside the root); the root is deleted when the trial ends. Claude trials also get OS-enforced read denial of this session's scratch area (keys, briefs, brains, other trials), the repo, the vault and personal folders (checked: a script run by the model got PermissionError on those and could read its own folder). Codex has no read denial, so every command a trial runs, and every tool call and result of a Claude trial, is scanned by code for real paths outside the trial's root (plus whole-disk and Spotlight searches); allowed are system programs, Python's libraries, the CLIs' own temp folders and Codex's built-in spreadsheet skill, which ships with Codex. A trial that reaches outside is discarded (answer kept in the record, never judged) and re-run in a fresh root; a second reach drops the pair, reported. Judges run the same way: their own root with only the brief, the reference, the schema and the two answers; the A/B key is kept outside it; the GPT judge's commands are scanned the same way.
13. **Isolation v4, before any counted trial (2026-09-26 12:30).** A first pass under item 12 (25 trials) showed the checks were still not tight enough, so every one of those trials is set aside as a pilot (kept in `pilot_v2/`, never judged or analyzed) and all trials are run again under v4. What the pilot showed: GPT-5.6-Luna's built-in spreadsheet plugin sent it searching the home folder for tools; one Sonnet run searched the whole disk for its own file name; Claude runs used Claude's shared temp folder, where one left a copy of a hotel brain workbook (`p.xlsx`) and another a dump of the payroll workbook, both findable by a later trial; one Haiku run executed a stale analysis script left in /tmp by an earlier test. v4: Codex runs with plugins and apps turned off (`--disable plugins --disable apps`); Claude runs get OS-enforced read denial of this session's scratch, Zach's other sessions and old test sessions, the repo, the vault, personal folders, both CLIs' homes (except the trial's own transcript folder) and loose files at the top of /tmp and of Claude's shared temp, plus write denial of loose files in that shared temp (checked by a script run by the model: protected reads and writes fail, its own folder works); trials of the same business never run at the same time; the trial-created files found in the shared temp were moved out; and the detector flags, for both CLIs, other trials' folders, other trials' CLI folders, loose files in shared temp, stale files at the top of /tmp, and whole-disk or shared-folder searches, and for Codex (no OS denial) any protected place. The rule is unchanged: a flagged trial is re-run once in a fresh root; a second flag drops the pair, reported.
14. **Isolation v5 (2026-09-26 12:40).** The first 10 trials under v4 are set aside too (kept in `pilot_v4/`, never judged): Claude Code's shell safety checks asked for approval on some inline Python commands, which nobody can give in a headless run, and Sonnet 5 stopped and answered without reading the file. 15. **v5.1 (2026-09-26 12:31), during the v5 run.** A v5 trial wrote a script into `/tmp/claude/`, a second shared temp folder Claude's sandbox lets every run write to and read. The run was stopped; Claude runs now also get read denial there (checked: the shell still works, writing there and reading back fails), and the detector flags any reference to it (Codex has no denial, so for it the folder is protected). 16. **Detector counts only what a trial could read (2026-09-26 12:35, before any judging).** Under v5.1, Claude runs often write their own scratch files to Claude's shared temp and then cannot read them back (the OS denies it), and one Sonnet run merely named such a path in code that never ran; flagging those would re-run and drop pairs over places the trial provably could not read. Also fixed, same time: the whole-disk rule matched ordinary Python (a comment starting "Find" and a `'/'` string on one line, joined because tool calls were scanned as escaped JSON); tool calls are now scanned as plain text, and a search counts only when `/` or a shared folder is the command's own argument. ## Results (2026-09-26, analyzed as planned, then checked by an independent pass)

Data: 95 of 96 trials clean, 47 pairs judged (31 held-out, 16 development), 94 verdicts. Full evidence (every answer, verdict, key, brain, pilot and script): `~/lab/spreadsheet-brain-evidence/rigor-2026-09-26.tgz` (sha256 `6428ff3c21547c33da2f6fadbabc61ccf5295afda828f96e94dfe15b09d27858`); results and scripts in `evals/rigor-2026-09-26/`.

**Primary (held-out, 31 pairs):** open-request score 7.00 of 15 with the brain vs 5.06 without. Mean difference +1.94, median +2.5; the brain answer scored higher in 25 of 31 pairs. Wilcoxon signed-rank, two-sided: p = 8.7e-05 (tie-aware exact p = 7.7e-05). Pre-registered business-bootstrap 95% CI [0.53, 3.43].

**Secondary (held-out):** plain questions right 25% with the brain vs 5% without (judge 1: 23 of 93 vs 5 of 93); McNemar exact, 18 questions right only with the brain vs 0 only without, p = 7.6e-06 (judge 2: 17 vs 0, p = 1.5e-05; an independent regrade agrees with judge 1 on 184 of 186 grades and gives 19 vs 1, p = 4.0e-05). Mistakes the owner would catch: 6.9 vs 8.0, p = 0.003. Judge preference: brain better 25, no brain better 6, p = 0.0009.

**Breakdowns (described, not tested):** every model gains (Haiku +1.0, Sonnet +2.2, Opus +1.9, GPT-5.6-Luna +2.7); both judges agree (Claude +2.2, GPT +1.7; score correlation 0.91). By business: inventory +3.6 (7 of 7 pairs), rent roll +3.3 (8 of 8), payroll +1.2 (6 of 8), online orders -0.1 (4 of 8). Development set: +2.1 (11.4 vs 9.3), p = 0.001, 14 of 16.

**What the result does and does not show.**
- The pre-registered test passes, and the independent pass reproduced every number, confirmed the A/B mapping in all 47 pairs, and found no outcome-dependent error.
- The pairs are not independent in the way the test assumes: the brain varies only across 4 held-out businesses. At the business level the effect is 3 of 4 positive (a t-test on the 4 business means gives p = 0.11, 95% CI about -0.8 to +4.8), so whether a brain helps on a new business in general is not established at this sample size. The 4-cluster bootstrap CI is too narrow.
- The gain tracks how many of the owner's key rules the brain carried. Where the brain held them (inventory, rent roll) the lift is large; in online orders the tool asked about none of the key rules and one of its notes ("keep both" for repeated orders) misled the stronger models.
- The brains were filled by an agent owner from a complete brief, and the owners typed most key rules into free-text answers because the tool did not ask for them. The gain comes from correct rule-based numbers, not from echoing the brief: in pairs where neither answer got a keyed question right, the gain is +0.4 (p = 0.40).
- Answers often revealed their condition (every Sonnet and Opus brain answer cites the tab). Judges mostly scored the citation as a made-up tab, a bias against the brain; the 6 pairs with no citation cue gain +2.75 (p = 0.06, the smallest possible p for 6 pairs with one loss).
- Absolute quality stays low: 7 of 15 with the brain, 25% of plain questions right.

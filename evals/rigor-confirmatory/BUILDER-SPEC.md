# Builder spec: confirmatory test businesses

Given to each builder agent inline. Builders never read the spreadsheet-brain repo or anything about the tool.

| id | line of work | main file writer |
|---|---|---|
| landscape | residential landscaping and lawn care: crew job log and invoices | xlsxwriter |
| dental | dental practice: appointment and billing export | openpyxl |
| trucking | regional trucking: fuel, mileage and load log | xlsxwriter |
| nonprofit | community nonprofit: donations and grants ledger | openpyxl |
| gym | independent gym: memberships, dues and class attendance | xlsxwriter |
| tickets | live-music venue: ticket sales and settlements | openpyxl |
| autorepair | auto repair shop: work orders, labor and parts | xlsxwriter |
| lawfirm | small law firm: timesheets and billing | openpyxl |
| construction | home builder: job costing, subcontractor invoices against budget | openpyxl |

## What each builder makes (in its own folder)

1. **The workbook(s):** one or two .xlsx files, generated by a Python script with a fixed seed, written with the writer above. One to four tabs. The main table holds 1,000 to 8,000 data rows. Real-world mess is welcome: header rows that are not in row 1, exports stitched together, typed notes, odd codes, blanks. File and tab names read like a real business's.
2. **The owner's knowledge (at least 5 facts).** Things the owner of this kind of business knows that a new bookkeeper or analyst would get wrong from the file alone, and that change correct answers. Write what a real owner of this business would carry in their head. Do not work from a list of trap types, and do not design anything for an AI tool. The data must show the effect of each fact (the rows, codes or numbers are there), but nothing in the workbook may state the fact: no legend tab, no cell note, no header, comment or document property that explains it.
3. **owner_brief.txt:** written to someone playing the owner ("You are <name>, who runs <business>..."): the business, the files as the owner knows them, every owner fact in plain words, what they want from the data, and "if you are asked something this does not cover, say not sure".
4. **key.json:** `business`, `files`, `owner_facts` (list), `open_request` (one message the owner would send an assistant about the file: a real task with a real purpose, not a quiz), and `eval_questions`: exactly three plain questions, each an object `{"ask", "answer", "how", "needs"}`. `ask` is asked the way the owner would ask it (never naming the rule). `answer` is computed by code in the generator under the owner's rules and is one of: a number, a name (string), a list of names, or an object of named parts. `how` says in one or two sentences how the answer is computed under the owner's rules. `needs` lists which owner facts (by index in `owner_facts`, from 0) the answer depends on. Every question depends on at least one owner fact.
5. **naive_answers.json:** the answer to each question computed the obvious way, ignoring the owner facts. Every one must differ from the key by more than 1%, or be a different name.
6. **generate.py** and a **check.py** that recomputes every key answer from the saved workbook alone plus the owner facts, and prints PASS only if they match.

## Rules for builders

- Never read, list or search `~/lab/spreadsheet-brain` or anything about a spreadsheet brain, and never read another builder's folder.
- Invent everything: fictional names, places and companies. No real people or businesses.
- Never use an em dash in any file.
- Report only: the folder, the file names, the number of rows, and PASS or FAIL from check.py. Do not paste facts, questions or answers into the report.

## Verifier (a separate agent per business)

Reads the builder's folder. Recomputes every key answer independently from the workbook and the owner facts with its own code, checks that naive answers differ, searches every cell, note, header, tab name and document property for any statement of an owner fact (a leak), and checks that each question is asked without naming its rule. Reports only PASS or FAIL with a reason category (answer mismatch, naive equals key, leak, question names the rule, other), never the content. A FAIL goes back to the builder once with the reason; a second FAIL replaces the business with a fresh one in the same line of work.
